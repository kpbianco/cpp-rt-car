## Startup and rollback ordering

1. `start()` resets the per-runtime transaction and reports, then runs the
   existing read-only platform preflight.
2. The calling frame lane is inspected without mutation when requested.
3. Watchdog, executor, and device-service threads apply/read back policy on
   themselves, publish readiness, and wait on the atomic decision.
4. The runtime commits only after every created lane has reported and no
   required failure exists.
5. On failure, abort releases lanes only to exit. Device service/backend state,
   executor workers, and watchdog are then cleaned in existing reverse order.
6. Applied policy on an aborted owned thread is marked rolled back because the
   thread is joined; a later start resets all transaction/report state.

## Changed and preserved invariants

Changed:

- The C++ source API can borrow an immutable-capability current-thread policy
  provider and report verified policy, native errors, and rollback state.
- Linux runtime-owned threads can apply/read back the supported affinity,
  scheduler, and bounded-name subset before startup commit.
- Executor workers can select immutable `spin` or `yield` idle behavior.
- Runtime-owned executor, watchdog, and device-service lanes cannot enter work
  loops until the same per-runtime startup transaction commits.

Preserved:

- stable C ABI v8, 70-symbol allowlist/fingerprint, SONAME 8, device ABI v1,
  runtime-config schema 7, installed SDK inventory/targets, compatibility
  aliases, Apache-2.0, and release/support claims;
- M15-01 exact role/region inventory and memory-plan accounting;
- external frame, host-adapter, XDMA, and accelerator thread ownership;
- default affinity, scheduling, name, stack, and yield behavior when no policy
  is requested;
- no memory provider, custom stack, guard-page, NUMA memory, residency,
  locking, pinning, huge-page, prefault, or first-touch change;
- no policy lookup, native mutation, allocation, or new thread creation on
  callback and steady-state submission paths;
- multiple runtime instances retain independent provider, report, barrier,
  failure, and rollback state.

## Rollback and residual risks

Batch rollback is a source revert to the M15-01 baseline commit. There is no
data migration. Thread-policy mutation is scoped to runtime-owned threads;
aborted threads terminate, so no long-lived host-thread policy restoration is
required. The frame lane is verify-only.

Residual risks:

- FIFO/RR requests usually require host privilege and were tested only through
  injection plus compiled native calls, not successful privileged execution.
- Atomic wait/notify and pthread behavior still require the mandatory Windows,
  Clang, and ThreadSanitizer CI matrix.
- Provider implementations are borrowed and must retain immutable capabilities
  and allocation-free, nonthrowing methods through stop/destruction.
- Native application is sequential; a required partial application is rolled
  back by terminating the not-yet-committed owned thread, not by restoring
  fields on that doomed thread.
- `park`/`adaptive`, NUMA-node thread policy, and custom stack/guard ownership
  remain deliberately unsupported rather than receiving an unreviewed wake or
  allocation contract.
- The separate control-plane full validator remains blocked by its checkout
  permission/dirty-state boundary, although the M15-02 batch schema passed.

No successful privileged FIFO/RR scheduling, PREEMPT_RT deployment, custom

first-touch, residency, CUDA hardware, XDMA hardware, combined topology,
