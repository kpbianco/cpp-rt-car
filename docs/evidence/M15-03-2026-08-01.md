## Allocation, commit, and rollback ordering

1. Finalization resolves requested policy against provider capabilities.
2. Phase scratch, task scratch, and trace storage are created in logical order.
   Each allocation retains its provider and opaque ownership handle.
3. Required application and residency verification complete before the runtime
   accepts finalization. Best-effort native failure retries only the documented
   portable default and records the fallback.
4. A partial failure releases created regions in reverse order and retains
   inspectable failure/rollback reports while the runtime stays configuring.
5. Startup creates any supplied stack before its runtime-owned thread and binds
   it before thread entry. Existing policy readiness and commit barriers still
   prevent callbacks before all required application/readback succeeds.
6. Startup failure aborts and joins every started lane, reverses device/backend
   startup through the existing checked path, and only then releases stacks.
7. Normal shutdown joins device service, workers, and watchdog before releasing
   their stacks. Runtime-owned trace, task, and phase regions then release in
   reverse ownership order.

## Changed and preserved invariants

Changed:

- The additive C++ API can borrow a memory-region provider and reports resolved,
  applied, verified, fallback, native-error, residency, committed-byte, and
  rollback state.
- Phase scratch, task scratch, trace storage, and requested runtime-owned custom
  stacks use provider-owned contiguous allocations.
- Linux can apply supported guard, prefault, lock/pin, huge-page, NUMA-binding,
  first-touch, and residency operations during bounded lifecycle phases.
- Runtime-owned executor, watchdog, and device-service threads can use supplied
  Linux stacks whose storage outlives the thread and releases after join.

Preserved:

- stable C ABI v8, the exact 70-symbol allowlist and fingerprint, SONAME 8,
  device ABI v1, runtime-config schema 7, SDK/package inventory, compatibility
  aliases, Apache-2.0, and release/support claims;
- the M15-01 logical `planned_bytes` accounting and 1.2.1 control-aggregate
  topology; provider committed-byte closure is explicitly deferred to M15-04;
- external registered state, device buffers, backend storage, frame stacks,
  host-adapter stacks, and vendor stacks remain verify-only and are never owned
  or released by the runtime;
- portable defaults retain aligned-new storage and implementation-owned stacks;
- callbacks and steady-state lanes perform no provider discovery, allocation,
  policy mutation, file I/O, hidden thread creation, or spill execution;
- provider, handle, report, and stack lifecycle state remains per runtime.

## Rollback and residual risks

Batch rollback is a source revert to the M15-02 baseline. There is no data
migration. The active contract deliberately leaves exact physical accounting
and broader compatibility closure to M15-04.

Residual risks:

- Windows/MSVC and Clang behavior, installed-package consumers, determinism
  artifact exchange, and the complete sanitizer matrix require GitHub CI.
- The native Linux custom-stack minimum reflects platform pthread requirements,
  not every instrumentation runtime's preferred stack size; TSan warned on the
  intentionally small test stacks even though the tests passed.
- Lock, pin, NUMA, and huge-page success depends on host configuration and
  privilege. Local tests verify truthful success/fallback/failure reporting,
  not production placement or residency guarantees.
- Provider callbacks are borrowed and must remain alive, immutable in
  capabilities, and behaviorally correct through every allocation's release.
  A faulty provider that fails its release callback can still leak resources;
  M15-03 retains the failure rather than inventing ownership-independent cleanup.
- Native release errors are exceptional operating-system failures. The runtime
  attempts checked reverse release, but cannot safely reclaim a mapping after a
  provider or kernel refuses the matching release operation.
- Exact control-aggregate arena ownership and reconciliation of logical planned
  bytes with provider-rounded committed bytes remain the M15-04 boundary.
