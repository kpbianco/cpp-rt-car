## Implemented model and admission

The additive installed C++ API now binds a registered HAL-v2 command-batch
phase to one rate domain with a positive completion budget, positive bounded
per-phase in-flight limit, and one explicit payload role for every buffer
reference derived from the already copied M17 declaration. Replacement is
transactional while configuring. Legacy device phases are rejected from this
opt-in path without changing their ordinary frame behavior.

Finalization derives and freezes an immutable device-rate plan containing:

- canonical phase/domain/backend identity and copied command skeletons;
- logical buffer slice, access, and payload-role references without payload
  bytes, addresses, vendor objects, or borrowed caller spans;
- backend-local wait/signal timelines and completion timestamp-domain identity;
- per-reference half-open completion intervals
  `[release, min(deadline, release + completion_budget))`;
- per-phase, per-backend, Runtime-global, and exact completion-boundary demand;
- an instance-owned inspection report and exact MemoryPlan/control-ledger rows.

Admission uses checked integer arithmetic over the repeating reference
supercycle. Completions sort before releases at an equal boundary. Previous
cycle carry is seeded before the first release. Optional references remain
inspectable but do not supply capacity for mandatory feasibility. Same-backend
wait cycles, unprovable waits, multiple signal owners, cross-backend resources,
payload/declaration mismatches, unsupported timestamp identity, malformed
capabilities, arithmetic overflow, and phase/backend/Runtime/completion-batch
over-capacity plans fail transactionally.

Failed device-rate admission retains a fixed-size public diagnostic containing
the status, rejected phase, and first reference index. It publishes no partial
compiled plan, and a corrected successful finalization clears the diagnostic.

Compiled device phases are canonicalized by compiled phase order. Equivalent
binding call order therefore produces the same inspection order and checkpoint
graph identity. Completion budget, maximum in-flight demand, and payload roles
participate in graph compatibility identity. No-device and CPU-only hashing
retain their conditional pre-M21 paths.

## Exact admission fixtures

The focused cyclic fixture uses a 10 ns supercycle with mandatory device
releases at 0 ns and 6 ns, each with a 6 ns completion interval. The second
interval completes at 12 ns and contributes one previous-cycle carry at 0 ns.
The observed per-phase and global peak is exactly two. Reducing the phase limit
to one rejects reference 0. Moving both completion boundaries to 6 ns while
setting completion-batch capacity to one rejects the exact poll boundary.

The distinct-backend fixture adds a simultaneous 0 ns release on a second
backend. Admission succeeds at the exact Runtime capacity of three, with
backend peaks two and one. Rebinding both phases to one backend and adding
opposing waits on their separately owned timelines rejects the resulting
same-backend cycle. The payload mismatch fixture changes a declared read role
to output and is rejected before plan publication.

Public Runtime tests inspect the compiled backend, domain, completion budget,
in-flight limit, command kind/opcode, payload buffer/role/extent, signal
timeline, admission interval, timestamp-domain identity, and all new
MemoryPlan counts. Failed finalization can be corrected and retried. Reversed
device-binding call order yields an identical checkpoint graph ID; changing a
completion budget changes it.

now checks `git ls-files --stage` first and falls back to host metadata outside
a Git checkout. This is a verification portability repair, not a runtime or
release-contract relaxation. A successful rerun remains required.

The same initial CI attempt showed two inherited M20 wiring defects after all
focused M21 tests passed: `test_sbom.cpp` still invoked the pre-subcommand SBOM
CLI, and the portable-assurance image did not contain the script's required
`rg` utility. The allowlisted CTest wiring now runs the current
`verify-dependencies --policy` command directly, and the portable-assurance job
installs ripgrep before its pinned-toolchain check. Neither check is skipped or
weakened; successful replacement runs remain required.

## Claim boundary, residual risk, and rollback

This evidence establishes only additive C++ device-rate descriptors,
immutable mixed CPU/device reference-plan compilation, deterministic
checked-integer conservative admission, logical ownership/capacity/timeline/
payload-reference validation, bounded configuration/report storage,
identity/accounting integration, and the named portable RT0 static/unit
results.

It does not establish active device-rate dispatch or completion, CPU/device
payload transfer, sampled I/O, device WCET, controlled performance, physical
CUDA/XDMA/DAC/DAQ behavior, HIL, electrical correctness, field evidence,
latency, thermal/endurance behavior, RT1, RT2, Unreal integration, support
promotion, signing, publication, release, deployment, or production readiness.
Completion budgets and capabilities are declared admission inputs, not
measurements.

Residual risk remains in compiler/platform combinations and lifecycle,
sanitizer, package, and deterministic-artifact cases that require hosted CI.
Rollback is one coherent revert of the additive device-rate API, compiler,
admission/report storage, identity/accounting changes, tests, docs/contracts,
digest refresh, and this evidence. No device-rate execution, persistent data,
hardware state, support promotion, tag, release, or deployment is created by
this batch.
