## Lifecycle and isolation observations

- The full fixture observed service-one initialize, service-two initialize,
  backend initialize, and only then phase execution.
- Stop requested both services before backend shutdown. An injected first
  backend shutdown failure left the extension `cleanup_pending`, readiness
  false, and dependent service callable ownership retained. A second stop
  retried the backend and then shut service two before service one.
- An injected service request-stop failure was the returned first error while
  backend and independent service cleanup continued; retry invoked only the
  unresolved request and owner.
- An injected service shutdown `INVALID_STATE` remained a failure and retained
  ownership/readiness false. Retry did not repeat the successful quiesce or
  independently completed service shutdown and invoked only the unresolved
  shutdown owner.
- An injected service initialize failure rolled back without phase admission;
  the same finalized Runtime subsequently started and stopped successfully.
- Detach incremented the inspector generation, cleared callable tables, marked
  the row detached/readiness true, and caused the prior handle to fail without
  output mutation.
- Two Runtime instances using the same entry semantics received different
  owners, rejected cross-instance handles, held different service/backend
  instances, and produced the same semantic config/graph/replay IDs.

## Review, residual risk, and unperformed validation

Three bounded read-only agent audits reviewed ABI layout/packaging, Runtime
lifecycle/accounting, and validation/governance before integration. A later
independent system-risk review found that service shutdown
`RTFW_STATUS_INVALID_STATE` was incorrectly treated as proof of release. That
could report unload readiness while service ownership remained uncertain. The
review repair permits only `RTFW_STATUS_OK` to release a service, adds the
negative retry test above, and refreshes the reviewed release digests. These
agent audits are not the required human ABI/API, concurrency/lifetime/security,
or package/claim reviews.

## Rollback

Before rollback in an integration, require successful checked Runtime stop and
checked detach for every registered extension. Then revert the header, Runtime
surface/implementation, tests/fixtures/CI, package inventory, documentation,
checkers, release digest ledger, and this evidence as one coherent unit. Do not
unload code while readiness is false and do not reuse ABI version 1 for an
incompatible contract. There is no repository data migration or release action.
