## Public Unreal task API audit

### `UE::Tasks`

The documented public surface is `Engine/Source/Runtime/Core/Public/Tasks/Task.h`.

- `UE::Tasks::Launch` creates a `Private::TExecutableTask` for every submission.
- `Tasks/TaskPrivate.h` implements that creation with `new`; small tasks use an engine lock-free allocator and larger tasks use `FMemory::Malloc`.
- Public launch allocates a task and returns a handle without an admission result. The internal `TryLaunch` boolean describes immediate scheduling versus dependency-deferred scheduling, not bounded scheduler-capacity admission, and the public launch surface discards it. The adapter therefore has no public engine result from which it can report bounded acceptance or rejection to `rt::HostExecutorAdapter::submit`.
- The public handle's `TryRetractAndExecute()` can target one no-prerequisite task without an arbitrary scheduler drain, but it does not solve launch rejection or reusable-node ownership.
- The engine retains a separate internal task reference until completion or until the scheduler has attempted execution. The public API exposes completion, not a separate scheduler-reference-retirement proof suitable for adapter slot reuse.

### Rejected alternatives

- `LowLevelTasks::FTask` plus `LowLevelTasks::TryLaunch` has an embedded reusable node and a boolean launch result, but `Async/Fundamental/Task.h` explicitly says it is for task-system internals and that engine code should include `Tasks/Task.h` instead. It is not admissible under M19-02.
- `TGraphTask` dynamically allocates its task node and exposes no bounded rejection result.
- `FQueuedThreadPool::AddQueuedWork` returns `void`; the approved implementation uses a critical section and a dynamically growing priority queue. Retraction also takes the critical section. It is neither bounded nonblocking submission nor bounded nonblocking help.
