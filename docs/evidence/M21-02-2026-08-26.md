## Claim boundary

This batch establishes portable RT0 software behavior for admitted active
HAL-v2 command-batch release dispatch and poll-only terminal completion. It
does not establish CPU/device payload publication, sampled I/O, active replay,
physical CUDA/XDMA/DAC/DAQ behavior, HIL, controlled performance, latency,
RT1, RT2, Unreal integration, support promotion, signing, publication,
release, deployment, or production readiness. M21 and CAP-M21 remain
incomplete.

## Implemented vertical

- `DeviceCallbackContext` appends a nullable `rate_release` pointer while
  preserving the earlier positional aggregate prefix.
- Finalization retains one direct device-plan index per reference release,
  offset-indexed device prerequisite slices, and preallocated generation-
  tagged completion tickets. Runtime dispatch does not rescan the graph,
  backend registry, buffer registry, or timeline registry per release.
- A due admitted provider runs exactly once through the existing selected
  executor path. Runtime validates and copies its complete fixed-capacity
  materialized batch and exact domain/phase/cycle/sequence/substep identity
  into an existing backend queue slot.
- Active rate batches release the selected executor phase after enqueue rather
  than holding its ordinary graph token. Independent same-group device records
  can therefore be outstanding together. A dependent CPU/device record first
  consumes its precomputed device prerequisite tickets; a successful release
  group consumes every remaining ticket before returning.
- Existing per-backend submission lanes retain sole active-path vendor-submit
  ownership. The existing service lane retains poll and submitted-timeout
  cancellation ownership. M21-02 creates no lane or thread.
- Runtime clamps a finite provider timeout to the earlier checked completion-
  budget or release-deadline remainder. A submitted/submitting timeout is
  settled once, issues at most one cancellation request, and enters a non-
  reusable terminal quarantine. A late completion is validated but cannot
  publish timeline progress or convert timeout to success. Successful checked
  backend shutdown is the reclamation boundary.
- Ordinary M17 command-batch execution retains its executor-token completion
  behavior. Existing stable statuses, device metrics/traces, active-rate
  actions, and schemas are reused.

## Ownership argument

The rate slot state extension is finite: `queued`, `submitting`, `submitted`,
existing early/completion-ready ownership states, `rate terminal`,
`rate-quarantine-owned`, `rate quarantined`, and `free`. Queue/submission/
service owners claim transitions with one atomic compare-exchange. Normal
terminal completion remains non-reusable until the host consumes the exact
slot-index, batch-id, and complete copied release identity. Timeout claims
vendor-owned states before cancellation and publishes quarantine only after
recording the terminal status. Submission return and late poll completion
observe the quarantine state and cannot recycle or settle it. Checked shutdown
releases retained rate slots only after backend ownership succeeds; failed
shutdown retains them for retry.

## Exact accounting

`MemoryPlan` appends source-compatible counters for retained reference indexes,
device-dependency entries, completion-ticket slots, and their exact bytes.
Those bytes are included once in `rate_dispatch_state_bytes`,
`rate_plan_bytes`, `runtime_control_bytes`, and the existing Runtime logical
control extent. The six-row planned-memory equation, provider regions, backend-
reported bytes, and installed C ABI memory-plan shape are unchanged.
