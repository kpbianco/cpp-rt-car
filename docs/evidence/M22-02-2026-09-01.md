## Public surface

The existing `LiveControlUpdateRecord` remains exactly 128 bytes. M22-02
appends `missed` to the live-control admission result and adds:

| Type | Fixed size | Purpose |
| --- | ---: | --- |
| `LiveControlBoundaryTarget` | 40 | Exact host-frame or compiled reference-release identity |
| `LiveControlRecordView` | 144 | Copied fixed record plus callback-lifetime read-only payload span |
| `LiveControlGenerationView` | 80 | Runtime/configuration-bound nonzero identity, target, ordered survivors |
| `LiveControlCommitInfo` | 128 | Latest published target/identity, survivor count, counters, staged occupancy |
| `LiveControlRecordStatusInfo` | 80 | Retained staged/committed/replaced/missed/stopped record status |

`CallbackContext` and `DeviceCallbackContext` append a nullable
`live_control` pointer. It is valid only during that callback. Device callbacks
receive host spans; payload bytes are never moved to a backend implicitly.
New Runtime inspectors preserve caller output when the bounded history entry or
consistent snapshot is unavailable.

## Boundary and publication state machine

Each mailbox slot has the fixed states `free`, `writing`, `staged`,
`boundary_owned`, `committed`, `replaced`, `missed`, and `stopped`.

1. A producer wins the existing one-attempt mailbox claim, selects `free` or a
   safely reclaimable terminal slot, transitions it to `writing`, copies and
   zero-pads the payload, and writes the immutable record.
2. Release publication changes `writing` to `staged`. The host boundary first
   advances its frame cursor; a rate boundary first closes its exact copied
   reference-release identity. That atomic cursor/closed state is the
   producer-versus-boundary linearization point.
3. The boundary performs one fixed-storage scan. `staged` records for the exact
   target transition to `boundary_owned`; closed older targets become
   `missed`; future records remain `staged`. A producer still in `writing`
   completes and then records `missed` or `stopped` without exposing a partial
   slot. The frame owner never waits, retries, locks against, or executes
   producer work.
4. Candidates sort by mailbox identity ascending and mailbox sequence
   ascending. A later candidate replaces an earlier candidate only for the
   same mailbox identity and update kind.
5. Survivors and exact payload bytes copy into the inactive preallocated
   generation. FNV-1a over the exact target and ordered survivor identities and
   payload digests produces a stable nonzero generation identity. One release
   store publishes the complete inactive generation.
6. Source slots terminalize as `committed` or `replaced`. Generations own
   independent copies, so terminal slots can be reused without callback ABA or
   payload overwrite. Bounded inspectors and reclaimers use a nonwaiting reader
   gate; unavailable reclaimed history is reported as unavailable.

An empty boundary advances only its exact cursor/accounting and leaves the
previous data generation unchanged. Exact rate targets repeat one
finalization-time reference release, including its sequence; they are not
reinterpreted as recurring templates in later supercycles. Skipped/omitted
reference occurrences are expired as missed once the logical window passes.

## Determinism, failure, lifecycle, and accounting

- Canonical order is independent of registration order, producer scheduling,
  slot index/reuse, address, hash-table order, operating system, and compiler.
- Generation identity includes the exact target, mailbox/producer sequences,
  update kinds, and payload digests. Runtime arrival state, addresses, active
  slot, counters, wall time, and scheduling are excluded.
- Callback/device/watchdog failure does not roll back a published generation.
  M22-03 owns apply-failure rollback and canonical action history.
- Stop closes admission and future boundaries first. An in-flight producer
  finishes one bounded copy and records a whole stopped result; after execution
  quiesces, remaining staged records terminalize as stopped.
- Each enabled Runtime owns independent cursors, states, candidate storage,
  two generation record arrays, two generation payload arrays, counters, and
  inspection state. Handles and views cannot resolve into another Runtime or
  configuration generation.
- `LiveControlMailboxSet::control_bytes()` and logical extents include each
  mailbox/slot/payload, producer, copied rate target, candidate index, terminal
  state, cursor/counter/inspection field, and both generation stores exactly
  once. Disabled live controls still contribute zero live-control bytes and do
  not alter baseline graph/config/replay identity.
