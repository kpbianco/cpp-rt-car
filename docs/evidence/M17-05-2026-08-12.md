## Material finding

The existing public Runtime and native CUDA/XDMA candidate surfaces cannot
currently express the approved sample. Command/timeline discovery in
`rt/src/command_batch.cpp` deliberately sets the caller-owned output
`struct_size` and `extension_version` to zero before invoking
`get_capabilities`. Both native candidates reject that call before overwriting
the output:

- `rt/src/cuda_backend.cpp::CudaDeviceBackend::Impl::command_capabilities`
  requires `output->struct_size >= sizeof(*output)`;
- `rt/src/xdma_backend.cpp::XdmaDeviceBackend::Impl::get_command_capabilities`
  requires the same incoming size.

A prototype using the actual version-2 injected driver tables, actual
`CudaDeviceBackend` and `XdmaDeviceBackend` objects, and their unmodified
`hal_v2_registration()` results failed on the first Runtime registration with:

```text
sample configure failed: HAL v2 command/timeline capability discovery failed or was malformed
```

The corresponding executable and focused CTest both exited nonzero. The
failure happens before graph finalization or start, so no accepted batch,
device work, or borrowed-resource cleanup was outstanding.

The active batch forbids every path under `rt/include/rt/` and `rt/src/` and
explicitly requires the actual native registration paths without a substitute
HAL implementation. Fixing the callback/output-contract mismatch therefore
requires a preceding approved repair batch or an explicit M17-05 scope change.
No wrapper, duplicate backend, weakened gate, or false success was retained.

The missing positive behavioral test was not retained because its required
assertion is successful native Runtime registration and it deterministically
fails on the current implementation. A test expecting that failure would
codify the defect, while a disabled or unwired positive test would weaken the
gate. The test must accompany the approved Runtime-path repair.
