## Independent risk review repair

The review found one medium-severity inventory correctness defect. A requested
custom vendor/service role correctly reported unknown thread cardinality, but
`memory.external-thread-stack` still reported `cardinality_known == true` and
counted only the caller/host lanes. A later policy or residency consumer could
therefore treat an incomplete external-stack count as exact.

The repair makes any requested role with unknown cardinality propagate that
uncertainty to the external-stack aggregate. The existing host/custom ownership
test was corrected, and
`CpuMemoryPolicy.CustomUnknownCardinalityPropagatesToExternalStacks` was added
as the focused behavioral regression gate. The contract language now states
that an attached backend or requested unknown-cardinality external role makes
the aggregate unknown. No count was invented and device ABI v1 was unchanged.

## Changed invariants

- Added source-level CPU/memory policy schema 1 without changing runtime
  configuration schema 7.
- Added bounded, instance-owned requested/resolved reports with stable thread
  and memory accounting identities.
- Added exact requested-byte projections for planned and informational memory,
  while keeping physical/applied/verified fields explicitly zero or
  `not_attempted`.
- Propagated unknown custom/vendor thread cardinality to the aggregate external
  thread-stack inventory instead of presenting an incomplete count as exact.
- Added transactional policy replacement/recovery before successful
  finalization and immutable report access afterward.

## Residual risks and unperformed validation

- Device ABI v1 does not expose XDMA worker cardinality. The report therefore
  preserves a stable XDMA-I/O identity but marks its backend-owned cardinality
  unknown; later additive backend accounting must supply concrete counts.
- `accounted_bytes` is requested plan/informational accounting, not allocator
  overhead, RSS, committed pages, residency, locking, pinning, or physical
  memory evidence.
- Native Linux/Windows affinity, scheduling, custom stack/guard creation,
  NUMA placement, prefault, memory locking, host/device pinning, huge-page
  fallback, residency verification, and rollback transactions were not
  implemented or validated in M15-01.
- Timeout and cancellation behavior is not applicable to this synchronous,
  pre-start model-only transaction; failed-finalize rollback/replacement and
  recovery are covered.
- Required GitHub Linux GCC/Clang, Windows MSVC, ThreadSanitizer, determinism
  artifact exchange, installed-package/compatibility consumers, and hosted
  documentation/release jobs were not run. No commit, push, or PR was
  authorized.
- No physical hardware, HIL, field, RT1, RT2, Unreal, signing, release,
  deployment, staging, or production validation was performed or claimed.
